# Quality + UI audit, November 2026

Scope: the guest QR menu, the ordering flow, the bartender queue, analytics,
inventory + barcode, CSV import/export, branding settings, and the docs.
Reviewed by reading every page and route on branch `quality-2026-11` (cut
from `public/launch-prep`, which is two commits ahead of `main` and holds the
README, LICENSE and `/about`). `npm run check` passed clean before any change.

Each finding has a rank, a status, and where it lives. "Done" means fixed in
this branch (commit "Quality pass: a11y, states, mobile targets, docs").
"Deferred" means it needs an owner decision, a schema change, or more than a
polish-sized edit, so it was left alone on purpose.

Ranking: P1 = affects a guest or the bartender during service tonight.
P2 = affects a fork or a new operator on day one. P3 = polish.

## Summary

The app is in better shape than most Replit Agent projects: auth covers every
mutation, sessions live in Postgres, the public order endpoint is rate
limited, the guest bundle is code-split, and the status palette is tokenised.
The gaps are at the edges: what a guest sees when something fails, how small
the tap targets get on the phone, what a screen reader hears, and docs that
promise a migration the code does not do.

## Design critique

### Guest QR menu (`/menu/:slug`)

Hierarchy. The page does the right structural thing: sections in admin order,
drinks sorted within, one primary action per card. Three issues stand out on a
phone held one-handed:

- The sticky header spends its width on two text buttons ("Home", "Share")
  and squeezes the menu name between them. On a 375 px screen the name
  truncates at about 14 characters. The name is already in the hero or the
  page heading below; the header could carry icons only. Left as is (design
  choice), noted for the owner.
- The badge row is the busiest element on the card and the least useful at
  ordering time. A guest decides on name + description; "Stirred" and
  "Cold" are bartender vocabulary. See finding 21.
- "Request This Drink" was 36 px tall and sat at the bottom of a card that is
  mostly text. It is now 44 px (`min-h-11`), which also makes it the clear
  visual anchor of each card.

Readability. Body copy is `text-sm` (14 px) muted grey on near-white. Contrast
is 4.7:1, which passes, but at arm's length in low light it is marginal. Not
changed; a size bump would be a design decision for the owner. The per-menu
`backgroundColor` and `typography` overrides can push contrast either way and
the admin UI does not warn when a chosen combination fails; see finding 7 and
the branding notes below.

States. Loading has skeletons. Empty ("No drinks available on this menu
yet.") is fine. Error was missing: any fetch failure fell through to "Menu not
found", which tells a guest on flaky bar wifi to give up. Both guest pages now
show "Couldn't load the menu" with a retry button. The order status banner
already handled network failure gracefully ("Status temporarily unavailable,
retrying...").

Offline. There is no service worker and none is proposed: an ordering app
that looks alive while offline is worse than one that says so. The retry
button plus the banner's retrying state is the honest version.

### Ordering flow

The dialog is good: name optional, mocktail checkbox only when relevant,
notes field, clear primary action. Two gaps:

- Error messages. The server returns specific, guest-readable text for rate
  limiting, out-of-stock and inactive drinks. The client threw it away. It now
  shows the server's message when there is one.
- Length limits. Nothing stopped a guest from pasting a novel into notes. The
  inputs now carry `maxLength` 80 / 500, matching the bartender's edit form.

After ordering, the button flips to "Ordered" and the banner appears above
the menu. The banner does not announce for screen readers; it now has
`role="status"` and `aria-live="polite"`.

### Bartender queue (`/dashboard`)

This is the strongest screen. Oldest-first, wait badges that escalate on
configurable thresholds, chime + tab badge, keyboard shortcuts, menu-accent
stripe per row, 86 from the row. On mobile the collapsible cards are dense
but legible. Changes made:

- Action buttons in the mobile card were 32 px tall in a 2-column grid. Now 40
  px. The 10 px badge text is now 12 px.
- Icon-only buttons (chime, shortcuts, 86) now have `aria-label`s; the
  checkbox that was wrapped in a click-catching `div` now has an accessible
  name.

Not changed: the desktop table's "Notes" column truncates to 200 px, so a long
special request hides behind the detail drawer. A `title` tooltip would be a
cheap improvement; left for the owner.

### Analytics

Bar chart + table, filters for never-made and least-ordered, archived menus
hidden by default. The chart's x-axis labels rotate 45 degrees and need
120 px of height, which on a phone means the chart is mostly labels. The table
below carries the same data, so nothing is lost. No empty-state copy problem.
No changes.

### Inventory + barcode

Card layout on mobile, table on desktop, status-coloured borders, +/- stock
buttons. The barcode scanner uses a capture-button approach rather than
continuous decode, which is the right call for mobile reliability. The lookup
route now times out instead of hanging on a slow upstream. Camera failures
get a specific message per error type (denied, no camera, in use) and the
manual-entry path stays reachable (`BarcodeScanner.tsx`, lines 124-143).

### CSV import/export

Preview-before-write with per-row errors is exactly right. Templates mark
required columns. One footgun for a fork: the drinks template's example row
uses `menu-uuid-here`, so a first-time importer needs to export menus first to
learn the IDs. `docs/run-your-own.md` says so.

### Branding settings

Logo upload, welcome message, headline/body font presets, QR dot/eye style,
queue thresholds, rate limit. The font presets work end to end (all five
families are loaded in `index.html`). What is missing is a live preview: the
admin picks a font and has to open the landing page to see it. Deferred.

Per-menu colours (`backgroundColor`, `accentColor`, `sectionHeaderColor`,
`menuTitleColor`) have no contrast check. An accent used as a badge
background with white text (`landing.tsx`) will fail on a light accent. A
small WCAG ratio readout next to each colour picker would be a worthwhile
follow-up.

## Code and security notes

- Auth: single `admin` user, `timingSafeEqual`, login rate limit 10/15 min,
  Postgres-backed sessions, `sameSite: "lax"`, `secure` in production,
  fail-fast on missing secrets. `requireAuth` is on every mutation and admin
  read. Verified route by route in `server/routes.ts`.
- CSRF: no token, but `sameSite: "lax"` plus `express.json()` (which only
  parses `application/json`) means a cross-site HTML form cannot reach a
  mutating route with a parseable body. Acceptable for a single-admin app.
- Order spoofing: `POST /api/orders` is public by design (guests have no
  account). Protections: per-IP rolling-hour cap from settings, drink must be
  active and in stock, `menuId` must match the drink. Order IDs are UUIDs, and
  `GET /api/orders/:id` is public, so anyone holding an ID can read the guest
  name and notes. Unguessable in practice; documented here so the owner knows.
- `GET /api/settings` is public and returns the rate-limit threshold and the
  queue thresholds alongside branding. Harmless, but a `pick` of the branding
  fields would be tidier.
- Uploads: see finding 13. Object serving at `/objects/*` is public, which is
  what hero images need.
- CSV: 2 MB payload cap, 5,000-row cap, a hand-rolled parser that handles
  quoted commas and doubled quotes but not quoted newlines. Fine for the
  templates it ships; a multi-line description in a cell will split rows.
- Dependencies: `npm audit` was not run on this machine (no network policy
  check); the playbook step stands.
